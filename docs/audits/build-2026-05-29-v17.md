# Forensic audit — GOLDEN CHAIN build, wave 17 (2026-05-29)

This audit is the v17 critic-proof pass on top of the v12 baseline +
v13–v16 refinements. It scans for anomalies that **survived v12–v16**,
including the irony of v16 itself violating its own newly-added
"Link-rot pre-flight" rule.

The PDF baseline is **not** rebuilt by this wave. The reference build
remains:

  - 69 chapters, 259 A4 pages, ≈3.5 MB
  - sha256 `6d2e29ed32cc92b4aea32a0c639f7f16c646d94e1aa4adba97787869ec79293d`
  - build commit `f7c36a7` (post-v12)

## Methodology

The wave inherits the audit harness from v13–v16 and adds two new
probes:

  - **Cross-repo entry-point sweep** — for each new audit doc on disk,
    grep every entry point (`README.md`, `CLAUDE.md`, `AGENTS.md`,
    `docs/agents/agent-bootstrap.md`, the skill mirror) to confirm it
    is referenced from at least one of them.
  - **"Latest audit" pointer freshness** — three files carry a
    "Latest audit" / "Recent audits" pointer
    (`docs/agents/agent-bootstrap.md`, `README.md`, `AGENTS.md`).
    They MUST all converge on the most recent wave number.
  - **Stale "Last updated" footer scan** — `grep -rn "Last updated:"`
    must match the current wave.

Eight anomalies (P0 × 4, P1 × 2, P2 × 2) survived v16.

## P0 — critical (entry-point drift)

### P0.1 — v16 audit doc is orphaned (no entry-point links it)

`docs/audits/build-2026-05-29-v16.md` was created by v16 P0 but **no
entry point links to it**.

  - `grep -rn "build-2026-05-29-v16" --include='*.md'` → empty.
  - v15 introduced the pattern of linking the latest audit from
    README/CLAUDE/AGENTS "Recent audits" lists; v16 P0 fixed v15's
    broken link to v13 but **did not add its own row** to those lists.
  - Concretely:
    - `README.md` "Recent audits" stops at v15.
    - `CLAUDE.md` "Audits" stops at v15.
    - `AGENTS.md` "Recent audits" stops at v15.

This is the exact failure mode rule 10's new "Link-rot pre-flight"
subsection is supposed to prevent — every wave that adds a file MUST
verify it is reachable from at least one entry point. v16 violated its
own freshly-codified rule. v17 fixes both the symptom (orphan v16
doc) and the meta-bug (rule 10 needs an inverse: "Entry-point freshness
gate").

**Fix:** add a v16 row to all three lists in the same shape as v13–v15,
and ship an executable `scripts/check-link-rot.sh` that fails CI if any
`docs/audits/build-*-vNN.md` newer than the most-linked one exists.

### P0.2 — `docs/agents/agent-bootstrap.md` "Latest audit/migration/runbook" pointer is pinned to v12

```
- Latest audit: docs/audits/build-2026-05-29-v12.md
- Latest migration: docs/migrations/2026-05-29-v12-fixes.sql
- Latest runbook: docs/migrations/2026-05-29-v12-runbook.md
```

Four waves (v13/v14/v15/v16) have shipped on top of v12 with **no
update to this pointer**. Every new agent that opens the bootstrap is
sent four waves backwards. The skill mirror inherits the same staleness
because v15–v16 only rewrote relative→absolute URLs without bumping
the version numbers.

**Fix:** move "Latest" to point at v16 (audit only — v13–v16 are
audit-only waves with no migration/runbook, document that explicitly so
the pointer stays correct across audit-only waves).

### P0.3 — `*Last updated: 2026-05-29 (v12 build).*` footer is stale

End of `docs/agents/agent-bootstrap.md` (line 353) and the skill mirror
both still carry `*Last updated: 2026-05-29 (v12 build).*`. v13–v16
shipped without touching this footer. A reader who jumps to the end of
the bootstrap to confirm "is this current?" gets a v12 answer.

**Fix:** change to `*Last updated: 2026-05-29 (v17 wave; baseline still
post-v12 build f7c36a7).*` and codify the bump as part of rule 10
step 5.

### P0.4 — rule 10 title still claims "v9 → v12 pattern"

```
# 10 — Next-Wave Workflow (v9 → v12 pattern, normative)
```

The rule has been used continuously through v13/v14/v15/v16 (and now
v17). Its own title undersells its track record by **five waves**. A
critic reading the rule for the first time would reasonably ask "where
is v13–v16?" — the rule body even refers to v12 as "the four most
recent waves … v9, v10, v11, v12", which has been false for a month.

**Fix:** update title to "v9 → v16 pattern, normative" and rewrite the
opening paragraph to reflect v13–v16 all used the pattern.

## P1 — formal precision (executable gates)

### P1.1 — rule 10's "Link-rot pre-flight" has no executable script

v16 added the rule in prose but never shipped a script. Result: v16
itself orphaned its own audit doc (see P0.1). Prose rules without
executable gates are not enforceable.

**Fix:** ship `scripts/check-link-rot.sh` with three sub-checks:

  1. Every `docs/audits/build-*-vNN.md` is referenced from at least
     one of {`README.md`, `CLAUDE.md`, `AGENTS.md`,
     `docs/agents/agent-bootstrap.md`}.
  2. Every local `.md` link target resolves on disk (the 110-link
     scan v17 ran by hand becomes a one-liner).
  3. The "Latest audit" pointer in `docs/agents/agent-bootstrap.md`
     points at the **highest-numbered** audit on disk.

  - Exit code matrix: `0` clean, `1` broken links, `2` orphaned audit,
    `3` stale "Latest" pointer. Wire it into the link-rot pre-flight
    subsection of rule 10.

### P1.2 — `scripts-inventory.md` does not list the new link-rot script

When `scripts/check-link-rot.sh` lands (P1.1), `scripts-inventory.md`
must gain a row covering it, with rule reference (rule 10 §"Link-rot
pre-flight"), exit code matrix, and inputs. v15 introduced the
inventory; v16 added the pre-commit row; v17 closes the loop.
